# AI Interaction Guidelines - Squadify

This document contains behavioral rules and constraints for the AI assistant. These are not technical or business decisions, but instructions on how to interact with the developer and the codebase.

## 1. Scope & Autonomy
- **Strict Adherence**: Do not perform any refactoring, file creation, or code changes that were not explicitly requested by the developer.
- **Incremental Progress**: Focus only on the specific task described in the prompt. If a secondary improvement is identified, suggest it in the chat instead of applying it automatically.
- **Minimal Changes**: When applying a fix or a feature, keep the changes to the minimum necessary to satisfy the requirement, respecting the existing code style.
- **Modern Code**: Avoid using deprecated APIs, methods, or features. Always check for the most current and recommended way to implement a functionality.
- **Resource Management**: Never hardcode UI text (copys) in screens or components. Always use resource files (e.g., `strings.xml`) to support localization and maintenance.
- **String Placeholders Must Be Numbered**: Compose Multiplatform's resource string formatter only recognizes numbered placeholders (`%1$s`, `%2$d`, ...) -- its matching regex is literally `%(\d+)\$[ds]`. A bare `%s` (the format Android's own `strings.xml`/`getString(id, arg)` accepts) is silently left in the output, unsubstituted, with no compile-time or runtime error. Always write `%1$s`, `%2$s`, etc. in any `strings.xml` entry consumed via `stringResource(res, ...)` or `getString(res, ...)`.
- **No Backslash Escapes in Compose Strings**: Compose Multiplatform's resource strings (`composeResources/values*/strings.xml`) are shown exactly as written: unlike Android's own `strings.xml`, `\'` and `\"` are not unescaped, so "Couldn\'t" shows its backslash on screen. Write a plain `'` and `"` (both are valid in XML text). Only `app/androidApp/src/main/res` keeps Android's escaping.
- **Compose Multiplatform Doesn't Validate Vector Drawable XML at Compile Time**: A malformed `composeResources/drawable/*.xml` (e.g. an XML comment containing `--`, which the XML spec forbids anywhere inside a comment, not just as delimiters) compiles and packages without any error or warning -- `painterResource`/`vectorResource` only parses the file at runtime, when the composable that references it actually renders, and a parse failure there crashes the app (`SAXParseException`) rather than failing softly. A clean `./gradlew compile*`/`assemble*` is therefore not evidence a hand-authored vector drawable is valid. After writing or editing one, validate it as real XML (e.g. `python3 -c "import xml.dom.minidom as m; m.parse('path/to/file.xml')"`) before considering it done, and keep comments plain prose -- no `--` (use `:` or a comma instead), consistent with the general XML comment rule.
- **No Raw Exception Messages in UI**: Never surface a caught exception's `.message`, a stack trace, or any other raw exception/technical detail directly as end-user-facing UI text. This is a security issue (information disclosure) as well as a UX one -- exception text can leak internal class names, SQL, file paths, or business logic. Always map errors to a static, localized, user-facing copy from resource files instead.
- **UI-Driven Lifecycle**: For critical one-shot events (like Splash navigation), do not trigger actions in the `ViewModel`'s `init` block if they emit to a Flow/Channel. Instead, trigger the action from the UI's `LaunchedEffect` after the subscription is established to ensure events are never missed.
- **Modern Navigation**: Prefer bottom navigation (`NavigationBar`) for main screen areas (like Teams/Players) to provide a modern and accessible mobile experience.
- **Navigation 3**: A new screen is a `@Serializable` `Screen` subclass with its own `@SerialName` (its web address, never renamed once shipped), registered in `AppNavigation`'s `screens { screen<Screen.X> { entry -> … } }`, and reached through `AppNavigator` (`navigate`, `popBackStack`, a result on `previousBackStackEntry?.savedStateHandle`). Its arguments are strings and booleans (an enum travels as its name), so its route round-trips (`ScreenRoutes.kt`, `NavigationTest`). See `TECHNICAL_DECISIONS.md` §11.4.
- **Filtering Patterns**: A single-choice filter is the shared `SegmentedFilter` (`presentation/ui/components/SegmentedFilter.kt`), the match type's look (All · Official · Tournament · Friendly): one outlined bar, the selected segment filled with the bar's colour. For a fixed set the unselected segments show a 5-letter cut ("Offic."); for names (teams) pass `shorten = false`, and the segments keep their whole names and scroll inside the outline when they don't fit. A **sort** is the shared `FilterChipRow` with "Sort" as its `leadingLabel`, as in the call-up (white chips, a row that scrolls edge to edge; inside padded content pass `insidePaddedContent = true`). A segmented bar inside padded content whose options may not fit (the match record's half length) passes `shorten = false, insidePaddedContent = true`: the whole bar runs past the padding and scrolls sideways, instead of scrolling inside its outline. Don't build another control for either. Dropdown pickers (season, age group) stay `FilterSelector`, and a form's own choices (weekdays, intensity) aren't filters.
- **Grey Screens, White Sections**: Every screen's background is `ScreenBackground` (light grey), and its content sits in white sections outlined in grey: `SectionCard` (`presentation/ui/components/SectionCard.kt`), or a white `Surface` with `SectionBorder`. Nothing that needs to read as a card goes straight on the grey: a form's fields go in a section, and a text field always has a white fill. Sheets, dialogs, dropdowns and pinned bottom bars stay white. A date or time picker takes `squadifyDatePickerColors()` / `squadifyTimePickerColors()` (`components/PickerColors.kt`), so it stays white with the club's accent even when the phone is in dark mode. The live match console keeps its dark theme.
- **UI Design Reference**: Build client screens to match the [Squadify App design canvas](https://claude.ai/code/artifact/9e670517-957d-43d7-87bb-f280967bb7e0) (a Claude Design canvas) wherever it has a relevant artboard -- its layout, copy, and interaction notes take precedence over inventing a new look. It's a JS-rendered app and can't be read via a plain HTTP fetch; viewing it needs a real browser (e.g. the `claude-in-chrome` skill), and even then the canvas may not respond to automated scroll/zoom/click -- if an artboard isn't reachable, ask the developer for a screenshot rather than guessing at the design.
- **Screen Content Padding**: Every screen pads its content with the shared `ScreenPadding` (`presentation/ui/theme/Dimens.kt`: 16dp sides, 14dp top, 20dp bottom), via `Modifier.screenContentPadding()` or `ScreenPadding.Values` for a list's `contentPadding`. The same goes for a screen's loading and error states, and the sides of a pinned bottom bar use `ScreenPadding.Horizontal`. A form's main button goes in a `Scaffold`'s `bottomBar` as `PinnedBottomBar` (`components/PinnedBottomBar.kt`: 12dp above and below, plus the navigation bar's inset), with any error above it and no hint text under it. Don't hard-code a screen-level padding; cards, sheets and dialogs keep their own inner padding.
- **Compose Previews & Orientation Support**: Every Composable screen must ship with at least one `@Preview` composable (or multiple, e.g. light/dark) so it can be reviewed without running the app, and must support both portrait and landscape orientations (no fixed/locked orientation, no layout that only works in one). Verify this before considering a new or modified screen done.
- **Wide Screens**: A screen also works on a tablet, an unfolded foldable, desktop and web, using the shared helpers in `components/Adaptive.kt` (`TECHNICAL_DECISIONS.md` §11.5), never a breakpoint of its own: `useNavigationRail()` (the window's size class, from `material3-adaptive`) for a rail instead of a bottom bar, `isLandscapeLayout` to save height (side-by-side panes), `isWide` for two columns. A form or a list of single rows is no wider than 720dp, centred: `Modifier.readableWidth()` after a `verticalScroll`, `readableListPadding()` for a `LazyColumn`, and `PinnedBottomBar` already does it. Cards go in a `GridCells.Adaptive` grid.
- **Database Efficiency**: Always avoid O(N) complexity when accessing the database. Prefer batch operations (e.g., `inList`, `batchInsert`) over multiple individual queries inside loops to prevent the N+1 problem.
- **Scalability (Pagination)**: When creating list-based endpoints (GET), always consider or implement pagination (limit/offset) to ensure the system remains performant as data grows. A list that grows without bound (across seasons, or with every parent) pages: `limit`/`offset` from `Paging`, `limit + 1` rows read to set `hasMore`, its filters and search in the query (`SqlSearch.kt` for names), and `LoadMoreEffect` + `loadingMoreItem` in the app. A request without `limit` keeps returning the whole list for older app builds. A list held to a season, an age group, a team or a match can stay whole. See `TECHNICAL_DECISIONS.md` §68.
- **Match lists**: any list of matches (a team's, an age group's, the club's) uses `matchListSections` (`components/MatchList.kt`) rather than its own headings and rows, so they all look the same.
- **Documentation Maintenance**: Always review and update relevant documentation files (`REQUIREMENTS.md`, `TECHNICAL_DECISIONS.md`, etc.) when implementing changes that affect business logic, architecture, or system flows.
- **Database Schema Sync**: Whenever a change adds, removes, or alters a table, column, index, constraint, or enum in `Tables.kt` (or otherwise changes the database structure), always update the "Database Schema: Current State of the Art" section in `PROCESS_FLOWS.md` (ER diagram, constraints, enum reference) in the same change, so it never drifts from the real schema. `Tables.kt` is in `server/data` and shared with the coach server: a change to a table in `sharedTables` needs a migration in **each** server's `db/migration` folder in the same PR, and each server's schema test (`ClubsSchemaTest`, later the coach one) must pass.
- **Shared Code Serves Two Products** (from Phase 9, `TECHNICAL_DECISIONS.md` §72): `common`, `:server:core` and `app/shared` are used by both Squadify for Clubs and Squadify for Coaches. A change there must keep both apps and both servers compiling and their tests passing; anything only one product needs goes in that product's module. A change to a shared game table comes with a migration on both servers in the same change. Business rules (permissions, plan limits) are enforced on the server, never only in an app.
- **Game Use Cases Ask the `AccessPolicy`**: a use case about games (matches, call-ups, the live game, the record and report, stats) checks access through `AccessPolicy` (`server/core`, `domain/access`), never `CheckUserPermissionUseCase` directly, so it can be shared with the coach server (`TECHNICAL_DECISIONS.md` §72). If no method fits, add one to the interface and to `ClubAccessPolicy`, with the exact club check, and cover it in `ClubAccessPolicyTest`. Club-only use cases (members, permissions, training, club settings) keep calling `CheckUserPermissionUseCase`. Game use cases live in `:server:core` (`server/core`), which must stay free of Ktor, Exposed and club roles: what it needs from a server is an interface there, implemented in the server.
- **Test Coverage for Business Rules**: Whenever a change introduces or modifies a business rule (e.g. validation, eligibility, permission, or state-transition logic inside a Use Case), always add or update the corresponding unit test(s) in the same change. This mirrors the existing pattern of `CheckUserPermissionUseCaseTest` and must be kept up regardless of whether tests were explicitly requested.
- **Integration Tests on a Test Database**: Besides the mock-based unit tests, each server has integration tests that start the whole server on a real Postgres and call its endpoints, for what a mock can't check (Koin wiring, routes, migrations, SQL). They run on the server's own test database (`squadify_coach_test`; `squadify_test` for the clubs server once it has them), created when missing and dropped once the tests have run, never on a dev database (`squadify_dev`, `squadify_coach_dev`). A new server flow (an endpoint, a migration) gets one. See `TECHNICAL_DECISIONS.md` §72.

## 2. Communication
- **Conciseness**: Keep explanations brief and technical.
- **Verification**: Always confirm when a task is completed and wait for the next instruction before proceeding to a new phase of the roadmap.
