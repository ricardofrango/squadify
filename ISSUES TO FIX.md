# Issues to Fix

Findings from a full code analysis pass (backend use cases/repositories/security, server startup config, and the client's data layer), captured here so they don't get lost. Nothing in this list has been fixed yet — check items off as they're addressed, and keep this file updated per the `AI_GUIDELINES.md` documentation rules.

## Critical — access control model doesn't match requirements

Confirmed against the actual intended domain model (as described by the developer): `ClubRole.MEMBER` is for people who *work* at the club (coach/staff) and can hold multiple team assignments across multiple clubs — never a player or a parent/family member. Players and family members are a completely separate persona that should be scoped to their own club(s) and team(s) only. Neither half of that model is correctly enforced today.

- [x] **A plain club member sees the whole club, not just "the club."** In `CheckUserPermissionUseCase`, once a caller has *any* club role at `MEMBER` level or above, there was a branch that granted access immediately whenever no `teamId` was passed — with no check of `team_staff` at all. Every use case that lists data without a team filter (`GetTeamsUseCase`, `GetPlayersUseCase`, `GetSeasonsUseCase`, `GetAgeGroupsUseCase`, `GetOpponentsUseCase`, `GetMatchesUseCase` without a team filter) hit exactly this branch. So a `MEMBER` with zero `team_staff` assignments could list every team, player, match, season, and opponent in the club — when per spec they should see nothing beyond the club itself. Even a member who legitimately *is* a coach on Team A got the same unrestricted view rather than being scoped to Team A. (Multi-club, multi-team membership itself — coach on Team A, staff on Team B, even coach in a different club entirely — is fine structurally; `ClubMembers` and `TeamStaff` are independent per-row tables with no conflicting constraint. The bug was purely that nothing narrowed a member's *view* down to their own assignments.)
  **Fixed:** `GetTeamsUseCase`, `GetPlayersUseCase` (no-`teamId` path), `GetMatchesUseCase` (no-`teamId` path), `GetSeasonsUseCase`, and `GetAgeGroupsUseCase` all now scope down to only what the caller actually has access to -- a `TeamRole` assignment (coach/staff) or a linked player via `TeamPlayers`/`UserPlayers` (player/parent) -- instead of the whole club. Club admins/coordinators still see everything, unchanged. Per explicit direction from the developer, the filtering is per-entity (e.g. a coach with two teams in different age groups sees exactly those two age groups and the season(s) they belong to, deduped) and applies uniformly to every persona, including players and parents -- not just plain club members. `GetPlayersUseCase` and `GetMatchesUseCase` also each pick up their own team-scoped-read fix (`minTeamRole = TeamRole.STAFF` + `allowPlayerOrParentAccess = true` on the `teamId`-filtered path), the same class of bug already fixed elsewhere. `GetOpponentsUseCase` is the one deliberate exception: confirmed with the developer that opponents are low-sensitivity reference data with no team scoping in the model, so any club member can list them regardless of team assignment -- left unchanged. See `GetTeamsUseCaseTest`, `GetPlayersUseCaseTest`, `GetMatchesUseCaseTest`, `GetSeasonsUseCaseTest`, `GetAgeGroupsUseCaseTest`, and the updated `PERMISSION_TEST_MATRIX.md`.
- [x] **Players and family members have no authorization path at all — not a misassignment, a missing one.** `CheckUserPermissionUseCase` only ever queried `ClubMembers` (club role) and `TeamStaff` (team role); it had no branch that checked `TeamPlayers`/`UserPlayers` to ask "is this caller a parent or player linked to someone on this team/in this club?" That meant `GetClubDetailsUseCase`, `GetMatchesUseCase`, and `GetMatchDetailsUseCase` — exactly the things family members need per the requirements — had no mechanism through which a player or parent could ever pass, no matter how the invite/link data was set up.
  **Fixed:** added a new opt-in `allowPlayerOrParentAccess: Boolean = false` parameter to `CheckUserPermissionUseCase`. When `true`, a 4th check runs after the existing club-role/team-role checks fail: it reads the caller's linked players via `PlayerRepository.getPlayersByUser`, filters to this club, and (when a `teamId` is given) confirms one of those players appears in `PlayerRepository.getTeamPlayersByClub` for that team. Wired into the six read use cases that need it: `GetClubDetailsUseCase`, `GetTeamDetailsUseCase`, `GetTeamPlayersUseCase`, `GetTeamStaffUseCase`, `GetMatchesUseCase`, and `GetMatchDetailsUseCase` (the last of these also gained the `minTeamRole = TeamRole.STAFF` / `teamId = match.teamId` fix it was missing). The flag defaults to `false` and no write/mutation use case passes it — see the DESIGN INVARIANT comment on `CheckUserPermissionUseCase` and `PERMISSION_TEST_MATRIX.md`.
  - **Decision (discussed with the developer):** when this path is built, keep it in the same `CheckUserPermissionUseCase` rather than splitting into separate read/write functions — less churn across ~20 call sites. The invariant that players/parents must never gain write access is enforced by discipline + tests (see `CheckUserPermissionUseCaseTest`, `GetTeamDetailsUseCaseTest`, etc.) rather than by the type system: no write/mutation use case may ever pass a player/parent identity through this check. Revisit as a real read/write split if this ever gets misused. A matching comment is now on `CheckUserPermissionUseCase.kt` itself.
- [ ] **`TeamRole.PARENT` and `TeamRole.PLAYER` model the wrong thing and should likely be removed.** `team_staff` (backed by `TeamRole`) is specifically for people who work at the club — per the clarified model, a player or parent should never end up as a row in `team_staff`; their access is meant to flow through `TeamPlayers`/`UserPlayers` instead. The `PARENT`/`PLAYER` values on `TeamRole` are unused today (confirmed: nothing ever inserts a `team_staff` row with either role), and keeping them invites a future implementation to wire player/parent access through the wrong table.
  - **Decision (discussed with the developer):** deliberately deferred while fixing the access-scoping bugs above (`GetTeamsUseCase`, `GetPlayersUseCase`, `GetSeasonsUseCase`, `GetAgeGroupsUseCase`, `GetMatchesUseCase`) so that pass stayed focused. Not fixed yet -- still open, revisit separately. When it is tackled, check for any switch/`when` statements or UI code (e.g. role pickers) that reference `TeamRole.PARENT`/`TeamRole.PLAYER` before deleting the enum values.
- [x] **Admin/coordinator are supposed to be fully equivalent until billing exists, but two use cases already special-case `CLUB_ADMIN`.** `UpdateClubUseCase` (editing the club's own profile) and `UpdateClubMemberRoleUseCase` (changing a member's role) both require `minClubRole = CLUB_ADMIN` specifically, excluding `COORDINATOR`. Per the stated business rule — the only planned difference between the two roles is billing access, not implemented yet — a coordinator should be able to do both today.
  - **Fixed:** both use cases now pass `minClubRole = ClubRole.COORDINATOR`. See `UpdateClubUseCaseTest`, `UpdateClubMemberRoleUseCaseTest`.
- [x] **A team's season isn't validated against its age group's season.** `Team` carries its own independent `season_id` column separate from the one implied by `age_group_id`, and `CreateTeamUseCase` never checks the two agree, or that the given `ageGroupId`/`seasonId` even exist and belong to the calling club. A team could be created whose `season_id` points at a different season than its age group's actual season, with nothing to catch it. (The DB-level "cannot exist without" constraints from `age_group → season` and `team → age_group` are fine — both are non-nullable foreign keys — this is specifically about the redundant, unvalidated second path via `team.season_id`.)
  - **Fixed:** `CreateTeamUseCase` now loads the age group and validates it belongs to the request's `clubId` and `seasonId` before creating the team. See `CreateTeamUseCaseTest`.
- [x] **Team-scoped read use cases never set `minTeamRole`, so legitimate team coaches/staff are denied their own team.** `GetTeamDetailsUseCase`, `GetTeamPlayersUseCase`, `GetTeamStaffUseCase`, and `GetMatchesUseCase` (when filtered by `teamId`) all call `CheckUserPermissionUseCase(..., teamId = teamId)` without ever passing `minTeamRole`. Since the team-role branch only runs `if (teamId != null && minTeamRole != null)`, it never fires — so a coach or staff member who legitimately belongs to that exact team is currently **denied** access to its details/roster/staff, and only club admin/coordinator can pass. This is the mirror image of the "no teamId = too broad" bug above: that one over-grants when `teamId` is omitted, this one under-grants when it's supplied. Surfaced while building `PERMISSION_TEST_MATRIX.md`.
  - **Fixed:** all four now pass `minTeamRole = TeamRole.STAFF` alongside `teamId`, so both coaches and staff of that specific team can pass. See `GetTeamDetailsUseCaseTest`.

## Critical — security

- [x] **Hardcoded JWT signing secret.** `server/.../security/JwtConfig.kt` had `SECRET = "my-super-secret-football-manager-key"` as a literal in source, with a comment acknowledging it should come from an environment variable in production but didn't. Anyone with read access to the repo could forge a valid access token for any user, including a platform admin, and fully bypass authentication.
  **Fixed:** added `ServerConfig` (`config/ServerConfig.kt`), which reads the secret from the `JWT_SECRET` environment variable and refuses to start (`IllegalStateException`) if `APP_ENV=production` and it isn't set. In dev, a clearly-labeled fallback (`dev-only-insecure-secret-do-not-use-in-production`) keeps `./gradlew run` working with no setup. `JwtConfig.SECRET` now reads from `ServerConfig.jwtSecret` instead of a literal.
  - **Note:** did not end up using the `konf` dependency mentioned below -- plain `System.getenv()` is simpler and lower-risk for the two config values needed here (this was a judgment call made without the ability to compile-verify konf's API in this environment; happy to revisit if you'd rather standardize on konf for future config needs). `konf` is still declared in `server/build.gradle.kts` and unused.
- [x] **H2 web console exposed with `-webAllowOthers` and a blank DB password.** `Application.kt`'s `main()` unconditionally started `org.h2.tools.Server.createWebServer("-web", "-webAllowOthers", "-webPort", "8082")`, and `DatabaseFactory.kt` connects as user `sa` with an empty password. Anyone who could reach port 8082 got a full SQL console against the data with no real authentication barrier.
  **Fixed (console):** the console now only starts when `ServerConfig.environment != AppEnvironment.PRODUCTION`, and `-webAllowOthers` was dropped entirely -- H2's web server binds to localhost by default, so a browser on the same machine still reaches it exactly as before; the flag was only what let *other* machines connect, which was never actually needed for local dev use.
  **Left as-is (DB password):** deliberately did not change the blank `sa` password. H2 persists user credentials in the database file itself at creation time, so changing the connecting password without also migrating the existing local DB file's stored credentials would lock the current dev database out until it's recreated -- a real risk for a change that can't be verified by compiling here. Low residual risk in practice: the DB is a local file, and the console that could reach it over the network is now dev-only and localhost-bound per the fix above. Confirmed with the developer that H2 is dev-only by design (see `REQUIREMENTS.md`'s "Production Database" item and `TECHNICAL_DECISIONS.md` §3) -- a future move to PostgreSQL for production replaces this credential model entirely rather than patching it further.

## High — correctness / data integrity

- [x] **Refresh tokens never actually expire.** `RefreshTokens.expiresAt` is stored but the lookup never checked it against the current time — a refresh token worked forever until explicitly deleted.
  **Fixed:** the expiry check is a business rule, so it lives in `RefreshTokenUseCase`, not in a repository query. The interface method `findUserIdByRefreshToken(token): String?` became `findRefreshToken(token): RefreshToken?` (new server-internal `RefreshToken(userId, expiresAt)` model in `core/.../model/AuthModels.kt`); `ExposedUserRepository` just retrieves the row. The use case then rejects a token whose `expiresAt` has passed with `UnauthorizedException`, deleting the dead row as it does so, exactly as it rejects an unknown one. The stale "in a real app we should also check expiry" comment is gone. No batch sweep of expired rows was added — the happy path deletes on rotation and expired tokens are now purged on use; a cron sweep can come later if the table grows. See `RefreshTokenUseCaseTest` (in-memory `UserRepository` fake, no time logic of its own) and `PROCESS_FLOWS.md` §2.3.
  - **Design note (discussed with the developer):** an earlier version of this fix put the `expires_at >= now` filter in the Exposed query. Moved into the use case because per `TECHNICAL_DECISIONS.md` §1 the data layer only persists/retrieves and use cases own business rules — and because a query-level filter forced the test fake to re-implement that rule to be meaningful.
- [x] **Refresh token lifetime is miscalculated.** `JwtConfig.REFRESH_TOKEN_VALIDITY_MS = 36_000_000 * 24` computed to 10 days, not the 24 days documented in `TECHNICAL_DECISIONS.md` §5.
  **Fixed:** both token lifetimes are now expressed with `kotlin.time.Duration` (`30.days.inWholeMilliseconds` / `1.hours.inWholeMilliseconds`) so the values are unambiguous and can't silently overflow an `Int`. Per developer direction the refresh lifetime is now **30 days** (not the previously-documented 24); `TECHNICAL_DECISIONS.md` §5 updated to match. Access token unchanged at 1 hour. See `JwtConfigTest`.
- [x] **User status is never enforced.** `UserStatus` has `SUSPENDED` and `INACTIVE` states, but nothing in the authorization path (`CheckUserPermissionUseCase`, `CheckUserIsAdminUseCase`) checks a user's status — a suspended user with a still-valid token and existing club/team roles can keep acting on the system.
  - **Fixed in `CheckUserPermissionUseCase`:** now throws immediately if `user.status != UserStatus.ACTIVE`, before even the platform-admin bypass. See `CheckUserPermissionUseCaseTest`.
  - **Still open:** `CheckUserIsAdminUseCase` isn't touched yet, and `LoginUseCase` still doesn't check status at all — a suspended user can still log in and get a fresh valid token today. Worth a follow-up.
- [ ] **No unique constraint on club membership.** `ClubMembers` has no unique index on `(club_id, user_id)`, and `ProvisionClubUseCase`, `CreatePlayersUseCase`, and `UpdatePlayerUseCase` all call `clubRepository.addMember(...)` unconditionally without checking for an existing membership first. Re-running any of these flows for the same person can silently create duplicate membership rows, potentially with conflicting roles.
- [ ] **Unguarded `Uuid.parse(...)` everywhere.** Every use case and repository parses path/body IDs with `Uuid.parse(...)` and no try/catch. A malformed ID throws a raw `IllegalArgumentException`, which isn't a `FootballManagerException`, so it falls through to the generic `exception<Throwable>` handler in `Application.kt` and returns a 500 instead of a clean 400 for what is really a client input error.

## High — test infrastructure

- [ ] **`CheckUserPermissionUseCaseTest.kt` is stale and doesn't compile.** It references a `Role` enum, a `TeamRepository.isUserStaffOfTeam(...): Boolean` method, and a 2-arg `CheckUserPermissionUseCase(userRepository, teamRepository)` constructor returning a non-`Unit` value — none of which exist in the current codebase (confirmed via grep: no `enum class Role` anywhere, `isUserStaffOfTeam` survives only as a stale comment, the real constructor takes 3 params including `transactionManager`, and the use case returns `Unit`). It needs to be rewritten against the current API, not extended. See `PERMISSION_TEST_MATRIX.md` for the persona/scenario matrix to base the rewritten tests on.

## Medium — performance / consistency

- [ ] **`getClubsByUser`'s join can fan out badly.** `ExposedClubRepository.getClubsByUser` chains `Clubs leftJoin ClubMembers leftJoin Players leftJoin UserPlayers` and dedupes with `.withDistinct()`. For a club with many players and guardians, this can multiply out to members × players × user-player-link intermediate rows before the final distinct — worth revisiting per the `AI_GUIDELINES.md` "Database Efficiency" rule.
  - This also no longer matches `TECHNICAL_DECISIONS.md` §3, which still claims "we use the `exists` operator with subqueries" — the code was refactored to LEFT JOIN + OR at some point and the doc was never updated.
- [ ] **No CORS configuration.** `Application.kt` never installs a CORS plugin. This is a KMP project with a separate `webApp` (JS/Wasm) target — once that client is served from a different origin than the API, browser calls will fail.
- [ ] **Unbounded WebSocket frame size.** `install(WebSockets) { maxFrameSize = Long.MAX_VALUE }` removes any cap on a single incoming frame — an easy DoS lever to close off.

## Low — style / consistency

- [ ] **`collectAsState()` instead of `collectAsStateWithLifecycle()`.** All 7 screens in `app/shared/.../presentation/ui/*` use plain `collectAsState()`. This was flagged as a recommendation in `TECHNICAL_DECISIONS.md` §11.3; confirmed by direct check to be 0-for-7 today.
- [ ] **Client config points nowhere real.** Both `DevAppConfig` and `ProdAppConfig` in `AppConfigs.kt` hardcode the same LAN IP over plain HTTP (`"http://192.168.1.84:8080"`, with the comment "For now the same address as requested") — credentials and tokens currently travel unencrypted, and "prod" isn't configured for anything resembling production yet.

## Already tracked elsewhere

These were found during earlier documentation passes and are tracked in `PROCESS_FLOWS.md` rather than duplicated here — see §11 (use-case gaps) and §12.5 (schema gaps) there:
- Inconsistent exception types for the same "not found" condition (e.g. `Team not found` throws `ValidationException` in some use cases, `NotFoundException` in others).
- `NotFoundException` isn't documented in `TECHNICAL_DECISIONS.md`'s exception hierarchy table.
- No pagination on any list endpoint, despite being called for in `AI_GUIDELINES.md`, `REQUIREMENTS.md`, and `TECHNICAL_DECISIONS.md`.
- No `onDelete` cascade/set-null strategy on any foreign key.
- Flyway is declared but never actually used; schema is created via `SchemaUtils.createMissingTablesAndColumns` plus a hand-written enum-normalization block instead.
- Hardcoded, machine-specific H2 JDBC path in `DatabaseFactory.kt`.
