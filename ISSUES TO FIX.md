# Issues to Fix

Findings from a full code analysis pass (backend use cases/repositories/security, server startup config, and the client's data layer), captured here so they don't get lost. Nothing in this list has been fixed yet — check items off as they're addressed, and keep this file updated per the `AI_GUIDELINES.md` documentation rules.

## Critical — access control model doesn't match requirements

Confirmed against the actual intended domain model (as described by the developer): `ClubRole.MEMBER` is for people who *work* at the club (coach/staff) and can hold multiple team assignments across multiple clubs — never a player or a parent/family member. Players and family members are a completely separate persona that should be scoped to their own club(s) and team(s) only. Neither half of that model is correctly enforced today.

- [ ] **A plain club member sees the whole club, not just "the club."** In `CheckUserPermissionUseCase`, once a caller has *any* club role at `MEMBER` level or above, there's a branch that grants access immediately whenever no `teamId` is passed — with no check of `team_staff` at all. Every use case that lists data without a team filter (`GetTeamsUseCase`, `GetPlayersUseCase`, `GetSeasonsUseCase`, `GetAgeGroupsUseCase`, `GetOpponentsUseCase`, `GetMatchesUseCase` without a team filter) hits exactly this branch. So today, a `MEMBER` with zero `team_staff` assignments can list every team, player, match, season, and opponent in the club — when per spec they should see nothing beyond the club itself. Even a member who legitimately *is* a coach on Team A gets the same unrestricted view rather than being scoped to Team A — `GetTeamsUseCase` always returns the full club roster of teams, never filtered to "teams this user is staff on." (Multi-club, multi-team membership itself — coach on Team A, staff on Team B, even coach in a different club entirely — is fine structurally; `ClubMembers` and `TeamStaff` are independent per-row tables with no conflicting constraint. The bug is purely that nothing narrows a member's *view* down to their own assignments.)
- [ ] **Players and family members have no authorization path at all — not a misassignment, a missing one.** `CheckUserPermissionUseCase` only ever queries `ClubMembers` (club role) and `TeamStaff` (team role); it has no branch that checks `TeamPlayers`/`UserPlayers` to ask "is this caller a parent or player linked to someone on this team/in this club?" That means `GetClubDetailsUseCase`, `GetMatchesUseCase`, and `GetMatchDetailsUseCase` — exactly the things family members need per the requirements — have no mechanism through which a player or parent could ever pass, no matter how the invite/link data is set up. This needs a third, genuinely new authorization path (reading `TeamPlayers`/`UserPlayers`) alongside the club-role and team-role paths that already exist — not a tweak to either of them.
- [ ] **`TeamRole.PARENT` and `TeamRole.PLAYER` model the wrong thing and should likely be removed.** `team_staff` (backed by `TeamRole`) is specifically for people who work at the club — per the clarified model, a player or parent should never end up as a row in `team_staff`; their access is meant to flow through `TeamPlayers`/`UserPlayers` instead. The `PARENT`/`PLAYER` values on `TeamRole` are unused today (confirmed: nothing ever inserts a `team_staff` row with either role), and keeping them invites a future implementation to wire player/parent access through the wrong table.
- [ ] **Admin/coordinator are supposed to be fully equivalent until billing exists, but two use cases already special-case `CLUB_ADMIN`.** `UpdateClubUseCase` (editing the club's own profile) and `UpdateClubMemberRoleUseCase` (changing a member's role) both require `minClubRole = CLUB_ADMIN` specifically, excluding `COORDINATOR`. Per the stated business rule — the only planned difference between the two roles is billing access, not implemented yet — a coordinator should be able to do both today.
- [ ] **A team's season isn't validated against its age group's season.** `Team` carries its own independent `season_id` column separate from the one implied by `age_group_id`, and `CreateTeamUseCase` never checks the two agree, or that the given `ageGroupId`/`seasonId` even exist and belong to the calling club. A team could be created whose `season_id` points at a different season than its age group's actual season, with nothing to catch it. (The DB-level "cannot exist without" constraints from `age_group → season` and `team → age_group` are fine — both are non-nullable foreign keys — this is specifically about the redundant, unvalidated second path via `team.season_id`.)
- [ ] **Team-scoped read use cases never set `minTeamRole`, so legitimate team coaches/staff are denied their own team.** `GetTeamDetailsUseCase`, `GetTeamPlayersUseCase`, `GetTeamStaffUseCase`, and `GetMatchesUseCase` (when filtered by `teamId`) all call `CheckUserPermissionUseCase(..., teamId = teamId)` without ever passing `minTeamRole`. Since the team-role branch only runs `if (teamId != null && minTeamRole != null)`, it never fires — so a coach or staff member who legitimately belongs to that exact team is currently **denied** access to its details/roster/staff, and only club admin/coordinator can pass. This is the mirror image of the "no teamId = too broad" bug above: that one over-grants when `teamId` is omitted, this one under-grants when it's supplied. Surfaced while building `PERMISSION_TEST_MATRIX.md`.

## Critical — security

- [ ] **Hardcoded JWT signing secret.** `server/.../security/JwtConfig.kt` has `SECRET = "my-super-secret-football-manager-key"` as a literal in source, with a comment acknowledging it should come from an environment variable in production but doesn't. Anyone with read access to the repo can forge a valid access token for any user, including a platform admin, and fully bypass authentication.
  - The `konf` configuration library is already declared as a dependency in `server/build.gradle.kts` for exactly this purpose (externalized config) but is never actually used anywhere in the code — it's the ready-made fix.
- [ ] **H2 web console exposed with `-webAllowOthers` and a blank DB password.** `Application.kt`'s `main()` unconditionally starts `org.h2.tools.Server.createWebServer("-web", "-webAllowOthers", "-webPort", "8082")`, and `DatabaseFactory.kt` connects as user `sa` with an empty password. Anyone who can reach port 8082 gets a full SQL console against the data with no real authentication barrier. Needs to be dev-only (or removed) before this goes anywhere near production.

## High — correctness / data integrity

- [ ] **Refresh tokens never actually expire.** `RefreshTokens.expiresAt` is stored but `ExposedUserRepository.findUserIdByRefreshToken` never checks it against the current time — a refresh token works forever until explicitly deleted.
- [ ] **Refresh token lifetime is miscalculated.** `JwtConfig.REFRESH_TOKEN_VALIDITY_MS = 36_000_000 * 24` computes to 10 days, not the 24 days documented in `TECHNICAL_DECISIONS.md` §5.
- [ ] **User status is never enforced.** `UserStatus` has `SUSPENDED` and `INACTIVE` states, but nothing in the authorization path (`CheckUserPermissionUseCase`, `CheckUserIsAdminUseCase`) checks a user's status — a suspended user with a still-valid token and existing club/team roles can keep acting on the system.
- [ ] **No unique constraint on club membership.** `ClubMembers` has no unique index on `(club_id, user_id)`, and `ProvisionClubUseCase`, `CreatePlayersUseCase`, and `UpdatePlayerUseCase` all call `clubRepository.addMember(...)` unconditionally without checking for an existing membership first. Re-running any of these flows for the same person can silently create duplicate membership rows, potentially with conflicting roles.
- [ ] **Unguarded `Uuid.parse(...)` everywhere.** Every use case and repository parses path/body IDs with `Uuid.parse(...)` and no try/catch. A malformed ID throws a raw `IllegalArgumentException`, which isn't a `FootballManagerException`, so it falls through to the generic `exception<Throwable>` handler in `Application.kt` and returns a 500 instead of a clean 400 for what is really a client input error.

## High — test infrastructure

- [ ] **`CheckUserPermissionUseCaseTest.kt` is stale and doesn't compile.** It references a `Role` enum, a `TeamRepository.isUserStaffOfTeam(...): Boolean` method, and a 2-arg `CheckUserPermissionUseCase(userRepository, teamRepository)` constructor returning a non-`Unit` value — none of which exist in the current codebase (confirmed via grep: no `enum class Role` anywhere, `isUserStaffOfTeam` survives only as a stale comment, the real constructor takes 3 params including `transactionManager`, and the use case returns `Unit`). It needs to be rewritten against the current API, not extended. See `PERMISSION_TEST_MATRIX.md` for the persona/scenario matrix to base the rewritten tests on.

## Medium — performance / consistency

- [ ] **`getClubsByUser`'s join can fan out badly.** `ExposedClubRepository.getClubsByUser` chains `Clubs leftJoin ClubMembers leftJoin Players leftJoin UserPlayers` and dedupes with `.withDistinct()`. For a club with many players and guardians, this can multiply out to members × players × user-player-link intermediate rows before the final distinct — worth revisiting per the `AI_GUIDELINES.md` "Database Efficiency" rule.
  - This also no longer matches `TECHNICAL_DECISIONS.md` §3, which still claims "we use the `exists` operator with subqueries" — the code was refactored to LEFT JOIN + OR at some point and the doc was never updated.
- [ ] **No CORS configuration.** `Application.kt` never installs a CORS plugin. This is a KMP project with a separate `webApp` (JS/Wasm) target — once that client is served from a different origin than the API, browser calls will fail.
- [ ] **Unbounded WebSocket frame size.** `install(WebSockets) { maxFrameSize = Long.MAX_VALUE }` removes any cap on a single incoming frame — an easy DoS lever to close off.

## Low — style / consistency

- [ ] **`collectAsState()` instead of `collectAsStateWithLifecycle()`.** All 7 screens in `app/shared/.../presentation/ui/*` use plain `collectAsState()`. This was flagged as a recommendation in `TECHNICAL_DECISIONS.md` §11.3; confirmed by direct check to be 0-for-7 today.
- [ ] **Client config points nowhere real.** Both `DevAppConfig` and `ProdAppConfig` in `AppConfigs.kt` hardcode the same LAN IP over plain HTTP (`"http://192.168.1.84:8080"`, with the comment "For now the same address as requested") — credentials and tokens currently travel unencrypted, and "prod" isn't configured for anything resembling production yet.

## Already tracked elsewhere

These were found during earlier documentation passes and are tracked in `PROCESS_FLOWS.md` rather than duplicated here — see §11 (use-case gaps) and §12.5 (schema gaps) there:
- Inconsistent exception types for the same "not found" condition (e.g. `Team not found` throws `ValidationException` in some use cases, `NotFoundException` in others).
- `NotFoundException` isn't documented in `TECHNICAL_DECISIONS.md`'s exception hierarchy table.
- No pagination on any list endpoint, despite being called for in `AI_GUIDELINES.md`, `REQUIREMENTS.md`, and `TECHNICAL_DECISIONS.md`.
- No `onDelete` cascade/set-null strategy on any foreign key.
- Flyway is declared but never actually used; schema is created via `SchemaUtils.createMissingTablesAndColumns` plus a hand-written enum-normalization block instead.
- Hardcoded, machine-specific H2 JDBC path in `DatabaseFactory.kt`.
